# ADR 0015 — Postgres + pgx + sqlc + chi

**Status:** accepted

## Context

The server needs to store share recipes, a trace cache, and compile job records.
Total expected data: kilobytes of shares, tens of megabytes of cached traces.
By volume, SQLite is the obvious answer.

## Decision

Postgres, accessed with `pgx`, queries generated by `sqlc`, migrations by
`golang-migrate`, routed by `chi`. No ORM.

## Alternatives

**SQLite.** Genuinely defensible on the data volume, and it removes an entire
service. Rejected for two reasons, one weak and one strong:

- *(weak)* multiple instances or a redeploy on ephemeral storage lose the cache.
  The cache is a pure cache, so this barely matters.
- *(strong)* **audience.** This is a portfolio artifact for backend roles, and
  the stack is one the author already knows well. A Postgres schema with proper
  indexes, a partial unique index doing real work, advisory-locked migrations on
  startup, and generated type-safe queries is *evidence*. SQLite would be the
  better engineering choice for the data and the worse choice for the purpose,
  and being clear-eyed about that distinction is itself the point.

Say this honestly if asked. "Postgres is overkill for the volume; I chose it
because it is the stack I want to demonstrate and because it costs me nothing
here" is a better answer than a manufactured technical justification.

**An ORM (GORM, ent).** Rejected: `sqlc` gives type-safe Go from real SQL, which
means the schema stays readable and the queries stay reviewable. An ORM hides
exactly the thing worth showing.

**No database — files on disk.** Rejected for shares (needs uniqueness and hit
counting), acceptable for the trace cache. Not worth two mechanisms.

**A cache service (Redis).** Rejected: the trace cache is read-mostly,
content-addressed, and small. Postgres handles it, and adding Redis would be
architecture for a slide.

## Consequences

- Migrations are embedded (`//go:embed`) and applied on startup behind a
  Postgres advisory lock, so concurrent instances do not race. Four lines, and it
  removes a class of deploy incident.
- `trace_cache.body` is stored **pre-gzipped** as `BYTEA` and served with
  `Content-Encoding: gzip` unchanged, avoiding a decompress/recompress round trip
  on every hit.
- A partial unique index (`WHERE status = 'ok'`) gives compile-artifact reuse
  for free: one successful compile per source hash, ever, while failures may
  repeat.
- `hits` / `last_hit_at` updated on read makes every cache hit a write. Fine at
  this volume; batch in memory and flush every 10s if it ever is not.
- Cost: a service to run, and the app cannot start without it. Mitigated by
  static-first (`BACKEND.md` §1) — the demo does not need the API at all.
